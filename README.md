# Дневник питания

Личный сервис с аналитикой по питанию. Данные лежат в Postgres на Supabase, точка ввода — Claude.

Раньше всё жило в `.md` и `.csv` в папке проекта, а `Аналитика.html` пересобиралась скриптом и вручную заливалась в артефакт. Теперь Claude пишет в базу, а админка читает её при каждом открытии — обновлять нечего.

## Из чего собрано

| Слой | Чем сделан |
|---|---|
| Хранилище | Postgres на Supabase, проект `pitanie` (ref `dhgkiphbkmstutalkhas`) |
| Ввод | Claude через MCP-сервер Supabase: функции `upsert_day`, `replace_dishes`, `log_weight`, `log_steps` |
| Админка | Next.js 15, читает базу только на сервере |
| Графики | Инлайновый SVG без библиотек |

Страницы: обзор с плитками и графиками, список дней, карточка дня с блюдами и нутриентами, недели, продукты, нормы.

## Что нужно сделать один раз

### 1. Ключи

В Supabase → Project Settings → API возьми `service_role` key. Это ключ с полным доступом: он живёт только на сервере и не должен попасть ни в браузер, ни в репозиторий.

Локально создай `.env.local` (он в `.gitignore`):

```
SUPABASE_URL=https://dhgkiphbkmstutalkhas.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service_role key>
ADMIN_PASSWORD=<пароль для входа в админку>
SESSION_SECRET=<длинная случайная строка>
```

`SESSION_SECRET` можно получить так:

```sh
openssl rand -hex 32
```

### 2. Запуск локально

```sh
npm install
npm run dev
```

Открыть http://localhost:3000, ввести `ADMIN_PASSWORD`.

### 3. Деплой на Vercel

```sh
npx vercel          # первый раз спросит про проект
npx vercel --prod
```

Те же четыре переменные добавить в Vercel → Settings → Environment Variables для Production. После этого админка открывается с телефона.

### 4. Перенос истории из файлов

Скрипт читает старые CSV и заливает их в базу. Запускать на маке, где лежит папка «Питание»: из облачной сессии до iCloud не дотянуться.

```sh
export SUPABASE_URL=https://dhgkiphbkmstutalkhas.supabase.co
export SUPABASE_SERVICE_ROLE_KEY=<service_role key>

# сначала посмотреть, что разобралось, ничего не записывая
python3 scripts/import_iz_csv.py "~/Библиотека/…/Здоровье и Медицина/Питание" --repetitsiya

# потом залить
python3 scripts/import_iz_csv.py "~/Библиотека/…/Здоровье и Медицина/Питание"
```

Скрипт идемпотентный: день перезаписывается целиком, блюда за дату заменяются. Гонять повторно безопасно.

Он переносит `Данные питания.csv`, `Блюда.csv`, `Вес.csv`, `Шаги.csv`, `Система питания.md` (в поле правил), `Отчёты/*.md` и, если получится разобрать заголовки, `Дневник питания.md`. Сколько записей дневника распозналось — печатает отдельной строкой; ноль означает, что заголовки в другом формате, и дневник стоит перенести руками или не переносить вовсе.

### 5. Нормы

Сейчас в базе стоят **заглушки** — 1900 ккал, 130 г белка и так далее. Открой страницу «Нормы» и поставь настоящие значения из «Система питания.md», иначе коридор и полоски на карточке дня будут врать. Если ты запускал импорт, текст правил уже подтянулся, а числа всё равно надо проверить руками.

### 6. Скилл

В `skill/dnevnik-pitaniya/SKILL.md` лежит обновлённая версия: она пишет в базу вместо файлов. Замени ею текущий скилл в настройках Claude — старый продолжит писать в несуществующие файлы.

## Как устроена база

Миграции — в `supabase/migrations`, применены к проекту как есть.

- `days` — итог дня. Вес и шаги здесь только если введены вручную.
- `dishes` — по строке на блюдо, привязаны к дню внешним ключом.
- `products` — словарь нормализованных ключей, пополняется триггером.
- `weight_log`, `steps_log` — односторонние входы из Apple Health, ключ — дата.
- `settings` — одна строка с нормами.
- `weekly_reports` — недельные разборы.

Витрина `v_days` — то, что читает админка: подставляет нормы, сводит вес и шаги (введённое вручную побеждает Health), считает скользящие средние за 7 дней и признак «в коридоре».

## Про доступ

RLS включён на всех таблицах, политик нет ни одной, гранты у `anon` и `authenticated` отозваны. У функций записи `EXECUTE` отозван не только у этих ролей, но и у `PUBLIC`: Postgres выдаёт это право каждой новой функции, а `anon` его наследует — без явного отзыва `upsert_day` вызывался бы публичным ключом через `/rest/v1/rpc`. Тот же отзыв прописан в `alter default privileges`, чтобы следующая миграция не открыла дыру заново.

Итого публичный ключ Supabase не даёт доступа ни к чему: читать и писать может только `service_role`.

Админка ходит в базу только на сервере и закрыта паролем — middleware пускает дальше лишь с подписанной кукой. Пароль один, пользователь один; это осознанное упрощение личного сервиса, а не заготовка под многопользовательский режим.
